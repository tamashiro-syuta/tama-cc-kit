# Medium フローの設計経緯

Medium フローの仕様は [tama-cc-devflow.md](./tama-cc-devflow.md) の「Router の判定ルール」「Medium フロー」「上限と停止条件」にある。ここには、なぜその形にしたかの根拠(過去セッションの実測)だけを残す。

## 課題

初期プロジェクトの変更はほとんどが追加(新規テーブル、新規エンドポイント、新規モジュール)で、壊す相手がまだ存在しない。それでも旧ルールの一発 Large 条件(DB スキーマ、API)に該当して Large に倒れ、時間がかかっていた。当初案は「Large から reviewer ループを抜いた Medium」だったが、実測を見て設計を変えた。

## 実測(2026-10-01 時点)

support-one / support-one-front の過去 10 セッション(Large 7、Small 3)の status.json とファイルの mtime から。

**レビューループは時間を食っていない。** Agent だけが動いている区間は数分で、ラウンドもほとんど回っていない。

| 指標 | 実測 |
|---|---|
| design.md → 最後の design-review | 2〜9 分 |
| 最後の result.md → 最後の impl-review | 1〜5 分 |
| 設計レビューのラウンド数 | 1 回: 5 件、2 回: 1 件、3 回: 1 件(認証フロー) |
| impl-review が 3 ラウンドまで行ったタスク | 76 件中 4 件 |
| design break の発生 | 0 件 |

**時間が溶けているのは Router と設計フェーズ、それにタスク数。** 人間の待ち時間を含むので上限値として読む。

| 区間 | 実測(セッション別) |
|---|---|
| 開始 → router.md(Router + clarify) | 23 / 37 / 43 / 50 / 51 分 |
| router.md → design.md(design + clarify + 承認待ち) | 26 / 71 / 75 / 123 / 147 分 |
| 実装フェーズ | タスク数 4〜25 件に比例 |

**reviewer は実質的な欠陥を拾っている。** impl-review の 1 ラウンド目は 76 件中 27 件(36%)が FAIL。相関サブクエリが外側の列を参照できず常に 0 を返す、`sanitizeReturnTo` が `//evil.com` を返しうる、モックの並び順が API 契約と逆、など。design-review も「RLS policy 適用後に全ログインが失敗する」を 1 ラウンド目で拾っている。

## 実測から導いた判断

- **reviewer は両方残す。** 削っても数分しか縮まず、36% の欠陥検出を失う。ループの上限だけ 1 往復に下げる
- **設計書を軽くする。** 設計フェーズが最大の時間消費で、追加だけの変更に異常系・ロールバック・可観測性・却下案を書かせても人間の読む時間が増えるだけだった。5 セクションにする
- **Router を軽くする。** Large 条件を grep で決まる「既存依存先を壊す / 既存テーブルの挙動を変える / 認証認可 / 不可逆」に置き換え、Small 条件を 9 項目から 4 項目に圧縮する
- **依頼を小さくさせる。** 時間はタスク数に比例する。フロー側で依頼を小さくはできないので、設計時点でタスクが 4 件を超えたら分割案を人間に提示して止まる
- **partial-redesign は Medium に持ち込まない。** 一度も発火していない
- **design は opus。** Medium が多数派になるので fable の消費を増やさない

「タスク 5 件以上は Large」という閾値は撤回した。過去の Large は全部 4 件以上で、Medium が空になる。

## 旧ルールとの振り分けの違い

過去の Large 7 件を新しい軸で振り分けると:

- Large のまま: rls-policy(既存テーブルの挙動を変える)、switch-tenant、list-my-tenants、auth-flow(認証)。いずれも設計レビューが実際に効いた案件
- Medium になる: team-staff-api(9 タスク)、audit-event(7)、change-ticket-customer(4)、customers-list(8)。設計レビュー 1 回で通り、design break もなく、時間はタスク数と設計フェーズに消えていた案件。4 件超なので分割提示の対象になる

## medium-flow を独立 Skill にした理由

実行するのが LLM なので、条件付きの手順より直線の手順のほうが踏み外しにくい。一番よく走る手順こそ直線にする。共通部分(Agent 定義、workboard、clarify)は既に別ファイルなので、重複するのはオーケストレーションの骨格だけ。
